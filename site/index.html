The same model, different accelerators.
How much do the answers actually change?

Nobody publishes this number. We are going to.

If you move an LLM from NVIDIA to AMD, Huawei Ascend, Intel Gaudi or AWS Trainium, the outputs will not be identical. Floating-point arithmetic is not associative, so different kernels reduce in a different order and the logprobs shift. That is expected and unavoidable.

The question that matters is how much — and whether the change you are seeing is ordinary numerical noise or a genuine porting fault. Today there is no public reference to answer that against.

The gap. Huawei's msprobe compares tensors at the operator level. MLCommons publishes 99%/99.9%-of-FP32 for a handful of benchmark models. vLLM's own Ascend accuracy CI accepts 5% drift against a hardcoded value with no GPU baseline column at all. Every one of them tells you to run an accuracy test. None of them gives you a number to compare against.

What the gate detects — measured

Before publishing accuracy deltas we had to establish that our own measurement works. We injected faults that mimic real porting failures and recorded whether the gate catches them, and at what magnitude. These are measured results, reproducible on CPU in seconds.

Two things we found while calibrating, which we would rather publish than hide

Cosine similarity cannot detect scaling errors. It is scale-invariant by definition — multiply every logprob by 1.01 or by 2.0 and it returns exactly 1.0000000000 either way. It is widely used for this purpose and it is the wrong instrument. We dropped it.

Max-absolute-difference over the full vocabulary is dominated by noise. Under BF16 the largest differences land on tokens with logprobs around −130 — probabilities near 1e-57, tokens that will never be sampled. Measured over the full vocabulary a correct BF16 port scores 0.4929; measured over the top 10 tokens it scores 0.0152. A threshold set on the former rejects every correct port.

Method

  • Black-box, over the wire. We compare two OpenAI-compatible endpoints. The harness never sees the silicon — only logprobs over HTTP.
  • Statistical, never bitwise. Bitwise equivalence across vendors is not achievable. Anyone claiming it is misleading you.
  • Worst case, not just mean. A mean over prompts hides the single bad position that actually matters. We report p50, p99 and max.
  • Full provenance. Weights SHA256, engine version, driver and toolkit versions, batch size, seed, and the prompt-set hash — published with every number.
  • Raw data published, not only the summary table.
ruitong port Qwen3-8B \
  --reference nvidia-a100=http://ref:8000 \
  --candidate amd-mi300x=http://cand:8000 \
  --output results/qwen3-8b__a100__mi300x.json

同一个模型，不同的加速卡。
输出到底变了多少？

这个数字没有人公开发布。我们来做。

把大模型推理从 NVIDIA 迁移到 AMD、华为昇腾、Intel Gaudi 或 AWS Trainium，输出不会完全一致。浮点运算不满足结合律，不同算子的归约顺序不同，logprob 就会发生偏移。这是预期之内、无法避免的。

真正关键的问题是差多少——以及你看到的差异，究竟是正常的数值噪声，还是一次真实的迁移故障。目前没有任何公开基准可供对照。

空白在哪里。华为 msprobe 在算子级别做张量比对；MLCommons 为少数基准模型公布 FP32 的 99%／99.9% 门限；而 vLLM 自己的昇腾精度 CI 允许对硬编码数值有 5% 的漂移，且完全没有 GPU 基线列。它们都让你去跑精度测试，却都没有给出可对照的数值。

正确的 BF16 迁移（0.0152）与最弱的注入故障（0.2341）之间相差 15 倍。正是这个间距，让门限具有实际意义。

校准过程中的两个发现——我们宁愿公开，也不愿隐去

余弦相似度无法检出缩放类错误。它在定义上就是尺度不变的——把所有 logprob 乘以 1.01 或乘以 2.0，返回值都精确等于 1.0000000000。这个指标被广泛用于此类比对，但它是错误的工具。我们已弃用。

全词表的最大绝对差被噪声主导。在 BF16 下，最大差异出现在 logprob 约 −130 的 token 上——概率约 1e-57，永远不会被采样到。同一次正确的 BF16 迁移，按全词表计算得 0.4929，按 top-10 计算仅为 0.0152。若按前者设定门限，任何正确的迁移都会被判为失败。

方法

  • 黑盒、走网络。我们比对两个 OpenAI 兼容端点。工具本身看不到底层芯片，只看到 HTTP 上的 logprob。
  • 统计意义，而非逐位一致。跨厂商的逐位一致无法实现，声称能做到的都在误导你。
  • 看最差值，而不只看均值。对 prompt 取均值会掩盖真正关键的那一个坏位置。我们同时报告 p50、p99 与最大值。
  • 完整溯源。权重 SHA256、引擎版本、驱动与工具包版本、batch size、随机种子、prompt 集哈希——随每个数字一同公布。
  • 公开原始数据，不只是汇总表。
